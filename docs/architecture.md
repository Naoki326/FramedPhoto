# 系统架构

```
┌─────────────────────────────┐        ┌──────────────────────────────────┐
│          服务端 (services/)  │        │          设备端 (firmware/)       │
│                             │        │                                  │
│  FastAPI                    │  HTTPS  │  ESP32 + GDEB0709E01            │
│  ├─ /devices   设备注册/心跳 │ ◄─────► │  ├─ WiFi 连接                   │
│  ├─ /contents  内容清单      │  polling│  ├─ HTTP 拉取内容清单 / 图片     │
│  ├─ /images    图片上传/转换 │        │  ├─ 图片解码 → E Ink 帧缓冲      │
│  ├─ /ota       固件发布      │        │  └─ SPI 驱动刷新电子纸           │
│  └─ 图片转换 (Pillow)        │        │                                  │
│     Spectra6 色板量化+抖动   │        │  组件: gdey_epd                 │
│                             │        │                                  │
└─────────────────────────────┘        └──────────────────────────────────┘
```

## 数据流

1. 用户在服务端上传/挑选照片（Web 或 API）。
2. 服务端用 Pillow 将图片按屏幕纵横比适配到 **1200×1600**（竖屏/方形 cover 铺满，横屏旋转 90° 铺满、文字随照片旋转），量化到 **Spectra 6 色板**（6 色 + 抖动），生成设备友好格式。
   - 天气卡片、日历卡片、自由模块文生图（即梦/通用接口）均以**横屏视角**（1600×1200）渲染/生成，经旋转适配后横放相框观看正立。
3. 设备按周期（或长连接/轮询）向服务端请求「内容清单」，拿到当前应显示的图片列表。
4. 设备下载图片数据（原始 RGB 或预量化格式），在本地拼出 E Ink 帧缓冲，通过 SPI 刷到屏幕。
5. 设备周期性上报状态（电量、当前显示内容、固件版本），服务端据此安排 OTA。

## 数据源与部署现状

- **照片数据源**：NAS `/volume1/photo` 单一共享目录（ADR-0007），经
  rsync over SSH 增量同步到本机镜像 `services/photos`（NAS 掉线不影响
  本地分析/每日精选）；管理台上传/建夹/改名/删除反向推回 NAS
- **部署**：macOS launchd 服务（`com.framedphoto.service`，开机自启 + KeepAlive），
  监听 `0.0.0.0:8010`，详见 `docs/development.md`

## 关键设计决策

- **转换放服务端**：E Ink 6 色量化 + 抖动算法复杂且迭代频繁，放服务端可免去设备端固件升级成本；设备端只做「格式解析 + 直接写显存」。
- **设备主动拉取（pull）**：设备发心跳拉清单，免去内网穿透/公网入站配置，也便于 NAT 后使用。
- **OTA 分双区（two OTA）**：分区表预留 app0/app1，固件上传服务端后设备后台下载并切换。
- **Monorepo**：固件、服务、文档同仓，便于整套方案版本对齐。

## 模块边界

| 模块 | 职责 | 不做什么 |
| --- | --- | --- |
| `gdey_epd`（组件） | SPI 总线、GPIO、命令序列、帧缓冲接口 | 不关心图片来源 |
| `main` 应用层 | WiFi、HTTP 客户端、调度、显示编排 | 不关心 EPD 命令细节 |
| 服务端 `epd_image` | 缩放/色板量化/抖动/格式封装 | 不关心设备硬件 |
| 服务端 API | 设备管理、内容、OTA | 不做图片处理细节 |
